# Спецификация (плановая): дорожная карта тестирования Т10–Т17

Статус: **запланировано** (задачи, реализация не начата). Источник: анализ
покрытия после веб-QA 1.2.4. Приоритет: Т10 и Т12 — высший (закрывают класс
проблем, найденный веб-QA), Т11 — дешёвый и сразу полезный.

## Т10 — Power-cut resilience (приоритет: высокий)

- **Контекст:** найден баг — пароль веб-админа не переживает перезагрузку
  (маркер CLOUD_INSTANCE_ID в MikoPBX). Класс риска: потеря данных при
  жёстком отключении питания в произвольный момент.
- **Сценарий:** установленная ВМ; жёсткий kill QEMU (`kill -9` процесса)
  в четырех точках: (а) сразу после применения пароля (~2 мин после старта
  контейнера), (б) середина `vlanit-update`, (в) середина `vlanit-backup`,
  (г) простой под нагрузкой. После каждого — загрузка → тест-агент.
- **Критерии:** система загружается; агент ≥95% проверок (допустимы
  WARN-CHECK upstream); btrfs без ошибок (`btrfs device stats` чистые);
  в сценарии (а) зафиксировать поведение пароля (ожидаем WARN-CHECK FAIL —
  известная проблема, не блокер).
- **Инструменты:** QEMU kill + существующий агент; точки kill по маркерам
  в serial-логе.
- **Оценка:** 1–1,5 дня (4 прогона × ~15 мин + разбор).

## Т11 — Performance baseline (приоритет: высокий, дёшево)

- **Сценарий:** в каждом прогоне Т2 замерять и записывать в
  `docs/testing.md`: время ISO→веб-АТС (по serial-маркерам), длительность
  установки (INSTALL_DONE − старт), время до готовности агента, размер ISO.
- **Критерии:** данные фиксируются; отклонение > 20% к прошлому релизу —
  повод разобрать (не автоматический FAIL: внешние факторы).
- **Инструменты:** временные метки в логах (уже есть), скрипт извлечения.
- **Оценка:** 2–3 часа.

## Т12 — Веб-QA регрессионный (приоритет: высокий)

- **Контекст:** веб-QA 1.2.4 выполнен вручную (Playwright) — страница входа,
  12 языков, отсутствие JS-ошибок. Нужен в каждом прогоне.
- **Сценарий:** после фазы 2 установки (ВМ жива с hostfwd): открыть
  `https://localhost:8443` (ignoreHTTPSErrors), проверить: код 200/302,
  заголовок, форма входа; вход admin + пароль из профиля → кабинет
  (HTTP 200, без pageerror); снять скриншот. JS-консоль: только штатные 401.
- **Критерии:** вход с паролем профиля успешен на ПЕРВОЙ загрузке
  (reboot-сценарий остаётся WARN-CHECK из-за upstream).
- **Инструменты:** Playwright (headless, MCP или скрипт); интеграция в
  test-qemu.sh как шаг фазы 2. Требует держать ВМ после PASS (сейчас
  test_install убивает ВМ — добавить флаг KEEP_VM=1).
- **Оценка:** 0,5–1 день.

## Т13 — WireGuard end-to-end

- **Сценарий:** две ВМ: «устройство» (1.2.4, WG включён) и «клиент»
  (второй QEMU с wireguard-tools, пиром устройства). Проверки: handshake
  (`wg show`), ping 10.66.66.1, SIP OPTIONS через туннель до АТС.
- **Критерии:** handshake ≤ 10 с; трафик идёт; после reboot устройства
  туннель восстанавливается автоматически.
- **Оценка:** 1 день.

## Т14 — unattended-upgrades глубже

- **Сценарий (агент):** к существующему `apt-security-source` добавить:
  `apt-get update` rc=0, список security-кандидатов получаем (пусто —
  норма для свежего релиза, важен непустой вывод sources), dry-run
  unattended-upgrades без ошибок.
- **Критерии:** новая проверка `apt-security-functional`.
- **Оценка:** 2–3 часа.

## Т15 — Интерактивный TUI-прогон установщика

- **Контекст:** интерактивный путь мастера покрыт только ручными прогонами
  (фидбек Александра). Автоустановка обходит диалоги.
- **Сценарий:** ВМ с ISO без autoinstall; через QEMU monitor `sendkey`:
  прохождение 7 экранов (enter, стрелки, ввод текста/паролей).
  Скриншоты на каждом экране (уже есть инфраструктура) + финальный
  INSTALL_DONE.
- **Критерии:** мастер пройден полностью; русский текст без квадратов
  (проверка скриншотов).
- **Инструменты:** monitor sendkey, screendump-серия.
- **Оценка:** 1–2 дня (хрупко, но ценно).

## Т16 — Стресс SIP

- **Сценарий:** SIPp (внутри контейнера или с хоста): 20 одновременных
  регистраций, 10 параллельных звонков 60 с. До/после: память/процессы
  контейнера (pids ≤ 4096), потерянные пакеты RTP, состояние агента.
- **Критерии:** без падения службы; pids < лимита; журналы без критики.
- **Оценка:** 1–2 дня (нужен SIPp + сценарии UAC/UAS).

## Т17 — Soak-тест (долгоживущий)

- **Сценарий:** ВМ работает 12–24 ч: периодический прогон агента (--quiet),
  лёгкий фоновый SIP-трафик. Контроль: утечки памяти контейнера, journald
  доходит до лимита 200M без ошибок, fail2ban не падает, btrfs
  `device stats` чистые.
- **Критерии:** нет деградации по метрикам за период.
- **Оценка:** 0,5 дня подготовки + машинное время.

## Общие требования к внедрению

- Каждый сценарий — отдельная проверка/набор в агенте или отдельный
  сценарий test-qemu.sh; результат фиксируется в `docs/testing.md`.
- WARN-уровень для зависимостей upstream; FAIL — только для нашего кода.
- Оценки: человеко-часы; прогоны — машинное время хоста.
