# Правила проекта VLANit PBX OS

Инструкции для любого агента/разработчика, работающего в этом репозитории.

## 1. Документируем настройки (обязательно)

**Любое изменение системных настроек устройства (Golden Image, установщик,
контейнер, сетевые/системные службы) сопровождается документацией в тот же
коммит или в коммит сразу после:**

- **README.md** — новый раздел или строка в «Системные настройки по
  умолчанию»: что настроено, какими значениями, где файл на устройстве.
- **Спека** в `docs/specs/` — для каждой версии/темы: корень изменения,
  принятое решение, отклонённые альтернативы, проверка (как подтверждаем).
- **architecture.md** — если изменение затрагивает архитектурные разделы
  (службы, диски, сеть, безопасность).
- **ADR** (`docs/adr/`) — если решение трудно обратимо или неочевидно без
  контекста (критерии: hard to reverse + surprising + реальный trade-off).

Формат фиксации настройки: что · значение · файл на устройстве · как
проверяется. Спека после реализации приводится к **as-built** состоянию
(фактические отличия от плана — зафиксировать, а не молча принять).

## 2. Сопутствующие правила (из практики проекта)

- **В git нет бинарников**: пакеты — через `tools/fetch-tools.sh` (манифест),
  генерируемые ассеты (PNG/PF2) собираются при сборке из SVG/скриптов.
- **Каждый релиз**: бамп версии во всех местах (build.yaml, release-manifest,
  os-release, имена ISO, README), запись в `docs/testing.md` (фактические
  результаты, число проверок агента), Release Notes в wiki.
- **Полевой фидбек**: пункты тестов на железе оформляются спекой
  (корень → решение → проверка) до или вместе с фиксом; известные открытые
  пункты честно перечисляются в notes релиза.
- **Тест-агент** — единый источник проверок: новая функциональность
  покрывается проверкой агента (id: одна фича — одна проверка).

## 3. Сборка и релизы через CI (с 1.2.6)

- **Workflow `build-iso`** (`.github/workflows/build-iso.yml`): push тега `v*`
  → сборка ISO из исходников тега → GPG-подпись контрольных сумм →
  публикация релиза с этим тегом (`--verify-tag`). Ручной запуск —
  `workflow_dispatch` (артефакт или `release: true`).
- **Правило релизов**: тег и файлы релиза после публикации не меняются;
  локально ISO не пересобираем «поверх» опубликованного релиза — бампим
  версию и идём через новый тег.
- **Подпись**: `scripts/sign-release.sh` подписывает `dist/*.iso.sha256`
  ключом релиза (pub — `rootfs/etc-vlanit-release.pub`, приватный —
  GitHub Secret `RELEASE_GPG_PRIVATE_KEY`). Проверка подписи — обязательный
  шаг при выкладке ISO из любого источника.
- **Релизный цикл**: `git tag vX.Y.Z && git push origin vX.Y.Z` — дальше CI.
  Версию бампить во всех местах ДО тега (build.yaml, release-manifest,
  os-release, имена ISO, README, docs/testing.md).
- **push workflow-файлов** требует scope `workflow` у токена (`gh auth
  refresh -s workflow`); без него GitHub отклоняет пуш.
- Документы: README «Правило релизов (CI)», идея #11 в
  `docs/ideas/engine-package.md` (РЕАЛИЗОВАНО).

## 4. Правила против овер-инжиниринга (ponytail)

Уроки аудита 2026-11-14 (issue #21–#28). Перед тем как добавить файл,
функцию, конфиг или параметр:

- **Каждый конфиг — с потребителем.** Новый ключ конфига добавляется
  вместе с кодом, который его читает. Файл конфигурации, из которого
  читается < половины ключей, — кандидат на удаление или на доведение
  до реального использования (единое место дефолтов — config/build.yaml,
  секция installer.*).
- **Нет мёртвого кода.** Функция/переменная добавляется вместе с
  вызовом. Перед коммитом: `grep -rn <имя>` — ссылок вне определения
  быть не должно.
- **Нет артефактов в git.** Выхлопы запусков (__pycache__/, *.pyc,
  отчёты сканеров, build/, dist/) не коммитятся; .gitignore покрывает.
  Проверка перед коммитом: `git status` + `git ls-files | grep -E
  'pyc|__pycache__'`.
- **Нет дублированной логики.** Правило, реализованное в двух местах
  (кавычкование quadlet, GPG-подпись), выносится в общий модуль при
  втором появлении, не при третьем.
- **Нет настроек «на вырост».** Параметр (passphrase, флаг, опция)
  добавляется, когда появляется первый реальный пользователь, не раньше.
- **YAGNI-вопрос при ревью своего diff:** «какой сценарий ломается, если
  это удалить?» — если ни один, не добавлять.
- Раз в квартал — ponytail-audit репозитория (dead code, фантомные
  конфиги, дубли), находки — issue с меткой tech-debt.
